## 0. 六项已锁定决策

| 决策 | 结论 | 理由 |
|---|---|---|
| **基座** | fork `dsh-wewrite` 0.5.3 成独立新插件包 | wewrite 是三者中唯一含完整 DSH 宿主代码、且已在本机 `~/.dsh/profiles/web` 实测装通的骨架（plugin_manager 确认 `wewrite→dsh-wewrite→include:wewrite` enabled+installed）。另两项目都不含宿主代码 |

| **发布**（m00379 追加） | **直接推送草稿箱为一等公民主路径**，手工粘贴降为次要路径；首推 `draft/add`、重推 `draft/update` 幂等覆盖，不自动群发 | 用户明确要求「对接公众号草稿接口，直接输出，不用手工粘贴」。wewrite 已有 `pushDraft` 底座，但存在静默丢图与重复建草稿两个缺陷，须修（§7.5 / §7.6） |

### 2.2 关键设计原则（从三个项目各继承一条）

1. **预览 = 产物**（wewrite AC-8）：`renderLayout()` 是纯函数、确定性。同 markdown + 同主题 → clean/stable/mobile/preview 四份产物字节可复现。宿主侧渲染，不经浏览器二次渲染。
2. **产物文件是唯一真相源**（pipeline）：report 里的 `clean_html` / `stable_html` / `mobile_screenshot_page` 字段名即文件名，下游一律从 report 取名，**任何代码不得自行拼文件名**。
3. **阶段机械推导**（aws）：文章处在哪一步由产物是否存在推导，不做人工状态机。

### 2.3 ★ 工程原则：在 wewrite 上**扩展**，不重写（本规划的总纲）

`dsh-wewrite` 是一条**已经跑通并经过真实生产验证的完整流程**（六步管线 + 引擎 + LLM 接入 + 门禁 + 渲染 + 9 家图片 provider + 微信推送 + 调度 + 客户端八页），v0.5.3 有 16354 行源码、28 个测试文件、约 430 个用例、11 个 E2E 用例组。**本插件以它为基座向上长，不另起炉灶。**

因此**任何改动都必须先归入下面三档之一**；归不进任何一档的，就是不必要的重写，不做。

| 档 | 含义 | 本规划的实例 |
|---|---|---|
| **A. 平台强制迁移**（不改就装不上/跑不起来） | DSH 0.2.0-rc.2 的契约变更，**与设计偏好无关** | Config 改 schemastery；工具入参改 JSON-Schema DSL；`agent/created` 改 `CreateAgentOptions.setup`；`inject` 硬依赖；`rpc.handle` 去 `authority`；客户端 `conversationEvents`→`uiConversation`、`turnTail` 改 list、槽位注册包 `slots.inject`（§15 全章） |
| **B. 输出契约扩展**（产物不够好，加密加厚） | **在 wewrite 现有模块上生长**，保持模块切分与不变量 | `src/render/`：主题 19 字段→~30 槽、3→6 套、加 `<span leaf>` 包裹、加三变体与合规检查器（§5）；微信推送加图片账本与幂等重推（§7.5/§7.6） |

#### 扩展发生在哪里，以及怎么跟上上游

**在本仓库 `evan3060/dsh-wechat-article`（`jerryjiao/dsh-wewrite` 的 fork）上就地扩展**（§0.1）。这带来一个必须提前定的纪律：

| 项 | 决定 |
|---|---|
| remote 布局 | `origin` = 自己的 fork；`upstream` = `jerryjiao/dsh-wewrite`（只读，仅 fetch） |

| 上游冲突的预期 | 上游处于 v0.5.3 且迭代活跃。**凡是 §2.3 三档之外的改动都要警惕**：那些最可能既非必要、又会持续产生冲突 |

**时机红利**：本仓库当前与上游 `identical`（`ahead 0 / behind 0`，HEAD `b62cd19`），**此刻做改名与 rc.2 迁移不会与任何上游新提交冲突**。越晚代价越大。

## 4. 管线：七步 run × 两组门禁

### 4.1 外层 run 步骤（★ 已按 §16.1 修订为七步）

```ts
export const PIPELINE_STEP_NAMES = [
  'topic',     // 选题：热榜聚合 或 固定主题
  'research',  // ★ 素材采集 + 源健康探针 + 研究门禁（§16 新增，补回上游被丢掉的「研究」阶段）
  'outline',   // 大纲：ctx.llm，骨架绑定（吃 research 结论定结构）
  'draft',     // 成稿：ctx.llm，两次自愈重试（吃 research 素材写内容）
  'gates',     // 内容质量门禁（wewrite 原生）
  'layout',    // 排版流水线八道门禁（§4.2）
  'images',    // 封面+正文图，唯一失败可容忍的步
] as const
```

> ⚠️ 本节的步骤表在 §16.1 从六步改成七步。**`research` 步的完整设计（源架构、探针四态、9 条研究门禁、预算与停手、去重与编号、领域配置外置）全在 §16。** 契约落差与必须同步修改的文件清单也在 §16.1。

**为什么保持 6 步而不是把 8 道门禁拍平成 run step**：run 记录要在客户端卡片上可读，且 `RunRecordSchema.steps` 复用 `StepRecordSchema`。八道门禁作为 `layout` 步的 `metrics.gates[]` 暴露：

```ts
interface LayoutGateMetric {
  index: number             // 1..8（推送前的第 9 道不在此数组，见 §7.5）
  name: 'render' | 'component-lint' | 'validate-clean' | 'validate-stable'
      | 'wrap-preview' | 'screenshot' | 'source-hash' | 'privacy'
  status: 'passed' | 'failed' | 'not-run' | 'not-applicable'
  blocking: boolean
  reason?: string
  reportPath?: string      // 相对 output 根
}
```

⚠️ **`gates` 步与第 3/4 道门禁不是一回事，别合并**：

- `gates` 步是 **wewrite 的内容质量审计**（`src/host/pipeline/steps/gates.ts`：15 个禁用词、内部标记残留、句长方差、信息密度、有序列表编号、图注序号 ↔ 图数、来源 URL 可见性与编造检测），判的是「**文章写得好不好**」；
- 第 3/4 道 `validate-clean` / `validate-stable` 是 **gzh 输出合规**，判的是「**HTML 能不能被公众号编辑器接受**」。

两者都硬、都在推送前必须过，但失败原因、修法、报告去向完全不同。合并会让「文案有禁用词」和「HTML 带了 `<style>`」挤进同一个 failed 状态，用户不知道该改稿还是该改排版。`gates` 步失败 → run failed，提示改稿；`validate-*` 失败 → layout 步 failed，提示改 Markdown 语法或换主题。

卡片上点开 `layout` 步就是 8 行门禁表，failed 的行标红并给出报告路径。

### 4.2 八道门禁的宿主实现映射

| # | pipeline 原步 | 本插件实现 | 门禁性 | 不一致说明 |
|---|---|---|---|---|
| 1 | `render_wechat.py` 非零即中止 | `renderLayout()`，产出 clean / stable / mobile + assets 复制 | **硬** | 缺图 → failed（等价 exit 2）；顺序错 → failed（等价 exit 3）；不支持语法 → failed（等价 exit 4，除非 `allowUnsupported`） |
| 2 | `component_lint.py` | **not-applicable** | — | ⚠️ **原门禁 lint 的是 gzh-design 组件库源码，不是文章**。本插件自研渲染器，没有 gzh-design 组件库 → 无对应物。**必须在 report 里写明理由，不得静默跳过、不得标 passed** |
| 3 | `validate_gzh_html.py` 跑 clean | `validateGzhHtml(cleanHtml)` TS 检查器 | **硬** | 判定规则见 §5.6 |
| 4 | `validate_gzh_html.py` 跑 stable | `validateGzhHtml(stableHtml)`，同一门禁跑第二次 | **硬** | 两份文档不同，必须各跑一次 |
| 5 | `wrap_preview.py` | `buildPreviewPage()` TS 自实现 | **硬** | 产出 `{tag}_预览.html`，含一键复制按钮 |
| 6 | `capture_mobile_screenshot.py` | **主路径**：客户端 390px 视口 iframe 实时预览（零依赖）<br>**增强**：`ctx.subprocess` 可选调本机 Playwright CLI 出 PNG | **软** | 失败/未装 → `screenshot_status='未运行'`，**绝不让 run 失败**。对应 pipeline 的 `ErrorActionPreference Continue` |
| 7 | 重算源 SHA256 + 写 `workflow-result.json` | `verifySourceUnchanged()` + `writeWorkflowResult()` | **硬** | 不一致 → failed，错误文案「安全检查失败：原始Markdown内容发生变化。」 |
| 8 | `sanitize_public_output.py` 非零即中止 | `sanitizePublicOutput()` | **硬** | 任何 error 级命中即 failed |

**净效果：排版步 6 硬 + 1 软 + 1 not-applicable；推送前另有第 9 道硬对账**（pipeline 原版是 7 硬 + 1 软）。

⚠️ **第 9 道不是第 9 个排版步骤**。它不写任何产物、不改 `screenshot_status`、不影响 `workflow_result.ok`，只是推送前的一次只读校验。放在推送流程里而不是排版流程里，是为了不让「能不能推送」污染「排版是否合规」这两个正交问题。

1. `PIPELINE_STEP_NAMES` 把 `'render'` 换成 `'layout'`
2. `PipelineDeps` 加 `layout: LayoutRunner`（与现有 `gates: GatesRunner` / `renderer: Renderer` 同形）
3. `layout` 步的失败**不容忍**（`images` 仍是唯一可容忍步，AC-9）

沿用不动的高价值设计（wewrite 报告 §3.1）：

- `begin(): { runId, done: Promise<string> }` 双形态 —— RPC 要立即返回 runId，agent 工具要 await 终态
- 每 run 一枚 `AbortController` + `completionWaiters` + `ABORT_SENTINEL`
- `awaitDone()` 对未知 runId 立即返回 `undefined`，不挂死
- `resumeInterrupted()` 开机把 `running|queued` 翻 `interrupted`，**不自动重跑**（AC-11 错过即错过）
- `pruneTerminalRuns()` 保留全部活动 + 最新 N 终态
- 引擎自己不落盘，一切经 `RunStore`

### 4.4 排版单独可跑（重要）

排版八道门禁**不只在管线里跑**。三种触发：

1. 管线 `layout` 步（成稿落库后自动跑）
2. Agent 工具 `wechat_layout(article_id | markdown, theme?, allow_unsupported?)` —— 改稿后重排
3. 客户端「排版」页手动触发

这要求 `LayoutRunner` 不依赖 run 上下文（除 `signal`），且产物落盘幂等（同名覆盖，允许重跑）。

### 5.2 `<span leaf="">` 包裹（gzh-design 硬要求）

pipeline 的每个**文本节点**都被 `<span leaf>` 包住（demo 50 处），这是 `validate_gzh_html.py` 数的量，跳不过。wewrite 现在没有这层。

移植方式：在 `blocks.ts` 与 `inline.ts` 的**每一个文本发射点**加一层：

```ts
// src/render/leaf.ts（新增）
export function leaf(text: string, style?: string): string {
  const s = style ? ` style="${style}"` : ''
  return `<span leaf${s}>${text}</span>`
}
```

要点：
- **每个渲染点一行改动**，但一个都不能漏 → 写一个结构断言测试：解析产物 HTML，对每个非空文本节点断言其父链上存在 `span[leaf]`
- 数字序号（OL 的 `01`/`02`、H2 的 `01`）本身也是文本节点，同样要包
- `<img>` / `<hr>` / `<br>` 是 void 元素，不包
- 属性名 `leaf` 无值（HTML boolean attribute），gzh-design 按属性存在性计数

⚠️ **待验证点**：`leaf` 是 gzh-design 的约定，本机无 gzh-design 检出，其校验脚本无法实跑验证（详见 §11 未验证清单）。移植后需要用户在装有 gzh-design 的环境里跑一次 `validate_gzh_html.py` 做交叉验证。

### 5.5 收紧 sanitize.ts（发布安全的必要改动）

现状 `src/render/sanitize.ts:45-48` 的 `ALLOWED_ATTRS` **放行 `class`**，且 `ALLOWED_TAGS`（32 个）比 gzh-design 宽。用于「粘进公众号」的场景必须收紧：

**记录键绝不入文件路径**（F15-F18）：domain 的 key 是 id/slug，文件路径只来自工作区解析，不来自用户输入拼接。

### 6.3 `ctx.fs` 的正确用法

宿主 `fs` 服务是文件读写的正道通道（不是 `node:fs`）：

- `fs.writeText(target, text, { atomic: true, expected: 'createIfAbsent' | 'replaceIfVersion' })` —— 带 sandboxPolicy
- `fs.editText(...)` —— 走 `FS_STALE_VERSION` 乐观锁
- `fs.watch(...)` —— 素材库与文章目录变更监听（aws 的 `watch.ts`）

⚠️ **只读原稿的强制**：`公众号排版` 下的 `终稿.md` 只读。原稿的 SHA256 前后比对（§4.2 第 7 步）是硬门禁，但代码层面还要**从不出现在原稿的写入目标集合里**。

## 7. 微信发布链路

**沿用 wewrite 的 `src/host/wechat/` 全套**（client 272 / egress 34 / diagnostics 57 / wechat-flow 61）作为底座，但**「直接输出到草稿箱」是一等公民路径**，不是手工粘贴的替代品 —— 两条路径并存，手工粘贴走的是同一份 stable 产物（粘贴不会丢图，因为图片已内联 data URI）。

本节改动共四处：7.1 内容来源、7.5 图片账本、7.6 幂等重推与回读、7.7 预检与错误处理。

### 7.1 内容来源：改用 stable 变体

```ts
// 现状（wechat-flow.ts:36）
const html = convertArticle({ markdown: article.markdown, theme: article.theme })
// 改为
const html = readLayoutReport(article.layoutRoot).stable_html   // data URI 内联版
```

理由：两条路径共用同一份产物，这是「不用手工粘贴」能成立的前提 ——

- **手工粘贴**（次要路径）：粘 `*_预览.html` 的复制按钮内容。stable 变体图片已内联 data URI，所以粘进公众号编辑器不丢图。
- **直接推送**（主路径）：`wechat/client.ts` 的 `replaceImageSources` 按**文档顺序**把 stable HTML 里的 N 个 `<img src>`（data URI）逐个换成 `media/uploadimg` 返回的 CDN URL，再 `draft/add`。data URI 版本让「推送」和「粘贴」两条路看到的是同一个字节序列，所见即所得。

**因此推送内容必须取 stable，绝不能取 clean**（clean 里是 `assets/…` 相对路径，推送出去微信侧取不到）。

**门禁前置**：`layout` 步未 succeeded → 拒绝推送（`WewriteServiceError('gates-not-passed', …)`）。这是对 wewrite 的**加强**：原版只看 `article.status`，现在还要看排版 report 的 `ok`。

### 7.2 publishTarget 纪律

`publishTarget: z.literal('draft')` 保留 —— freepublish 在**类型层不可达**（AC-10）。scheduler 产物永远只进草稿箱。

### 7.3 推送审批：双重 fail-closed

沿用 `src/host/agent-tools/push-approval.ts`：
1. `ctx.on('tools/pre-execute')` waterfall 返回 `{kind:'ask'}`；`ctx.on` 抛错或不返回函数 → **根本不注册推送工具**
2. `execute` 内二次 `isArmed()` 校验

追加到 `composePushAskReason` 的裁决信息：排版 8 门禁结论 + 隐私审计结论（`privacy-audit.json` 的 `ok`）。

### 7.4 egress 与诊断

沿用 `egress.ts`（`resolveApiBaseUrl` 单一出口）+ `diagnostics.ts`（40164 → `IP_WHITELIST` + `extractExitIp` + 两条出路）。单出口纪律（AC-2）不变。

### 7.5 推送必须配「图片账本」—— wewrite 现状会静默丢图

wewrite 的 `pushDraft` 有个会静默丢图的结构性缺陷（`client.ts:199-207` + `209-235`）：

```ts
const IMAGE_SRC_RE = /(<img\b[^>]*?\bsrc\s*=\s*)(["'])(.*?)(\2)/gis;
function replaceImageSources(html, uploadedUrls) {
  let index = 0;
  return html.replace(IMAGE_SRC_RE, (whole, prefix, quote) => {
    if (index >= uploadedUrls.length) return whole;   // ← 图片多于 URL 时静默保留原 src
    ...
  });
}
```

`replaceImageSources` 是**纯位置式**的：第 N 个 `<img>` 无条件对应第 N 个上传 URL。wewrite 的入参是 `bodyImageIds`（domain 里记账的配图），而正文里可能还有编辑器/管道插入的额外图；一旦 `<img>` 数 > `contentImages` 数，**多出来的图会保留 `assets/…` 或旧 data URI 原样送进 `draft/add`**，微信侧渲染成裂图，且没有任何报错。

本插件把「推送用了哪几张图」变成显式账本，`stable_html` 的每个 `<img>` 都有唯一对应的 `AssetIndex` 记录。

1. **排版期记账**：`renderLayout` 的 `imageResolver` 在解析每张图时同步产出 `imageLedger: { ledgerIndex, alt, assetId?, rawSrc, resolvedSrc, status }[]`，顺序即 `<img>` 出现顺序。`SourceIntegrity.images[]` 已是这个形状（`index/alt/raw_src/resolved/status/clean_src`），**直接复用，不新增结构**。
2. **推送前对账**（新增硬门禁，编号 9）：`assertPushableLayout(layoutRoot)` 逐条校验，任一不满足即拒绝推送**且不调用任何微信接口**：
   - `source_integrity.ok === true` 且 `source_unchanged === true`
   - `images[].status` 无 `missing`（`external` 允许，但要计数并在审批文案里显示「N 张外链图不会随草稿上传」）
   - `images.length === stable.html` 里 `<img>` 实际出现次数（用 `IMAGE_SRC_RE` 扫一遍），不等即判定「账本与产物脱节」→ 拒绝
   - `privacy_audit.ok === true`（errors 非空即拒）
   - `workflow_result.stable_html` 指向的文件存在且 SHA 与生成时一致（防产物被手工改过）
3. **上传改为账本驱动**：`pushDraft` 的入参从 `contentImages: readonly WeChatBinary[]` 改为按 `imageLedger` 顺序传 `contentImages`，**张数必须等于 `<img>` 计数**——不等在 client 入口就抛 `push-image-count-mismatch`，绝不让 `replaceImageSources` 走到 `index >= uploadedUrls.length` 那个静默分支。
4. **替换后校验**：`replaceImageSources` 改为返回 `{ html, replaced, skipped }`；`skipped > 0` 即抛错（等价于把原来的静默降级改成硬失败）。这是对 `client.ts` 的**必要偏离**，不是可选优化。

### 7.6 幂等重推：`draft/add` 首推，`draft/update` 覆盖

wewrite 只有 `draft/add`（`client.ts:168-197`），推一次就置 `status:'pushed'`。但用户会改稿重推 —— 每次 `draft/add` 都在草稿箱里**新增一条**而不是更新原草稿，箱子里堆积多份同标题旧版，且 `wechatMediaId` 只留最后一次，前面那些无从清理。

**推送状态机**（`ArticleRecord.pushState`，取代单一的 `status:'pushed'`）：

```
未推送 ──push──▶ pushed{ mediaId, thumbMediaId, contentSha, pushedAt, title, digest }
   ▲                   │
   │                   │ 内容变更（stable_html SHA 变 / 标题摘要变 / 配图集变）
   │                   ▼
   └──── confirm ◀── drifted{ mediaId, lastGoodSha, drift: {content?, title?, digest?, images?} }
                       │
                       └──repush──▶ pushed{ 新 mediaId = 同一草稿 mediaId, revision++, updatedAt }
```

- **首推**：`draft/add` → 记 `mediaId` + `contentSha`（= stable_html 的 SHA256）。
- **重推**：若 `pushState.mediaId` 已存在 → 走 `draft/update`（`POST /cgi-bin/draft/update`，body `{media_id, index:{…}}` 覆盖第 0 条）而不是 `draft/add`。`index` 固定 0，因为插件一次只建一篇单图文草稿。⚠️ **此路径未经实跑**，见 §13。
- **drift 检测**：推送前比对当前 stable_html/标题/摘要/配图集与 `lastGoodSha`，不一致先在 UI 标 `drifted` 并展示差异摘要，让用户决定，而不是静默覆盖。
- **回读校验**（`draft/get`）：推送成功后**可选**调 `POST /cgi-bin/draft/get {media_id}`，把微信侧返回的 `title`/`digest` 与本地比对，不一致时在 UI 亮黄灯「已推送但回读不符，请人工核对后台」。默认关闭（多一次 API 调用 + 多一个失败面），由设置项 `wechatVerifyAfterPush` 控制。
- **撤回**：`draft/delete` 插件**不实现自动撤回** —— 误删用户在后台手工改过的草稿不可逆，且撤回是破坏性操作，收益不抵风险。UI 只提供「后台位置提示 + mediaId 尾 4 位」，需要删除由用户自己去后台做。

### 7.7 预检、失败处理与可观测性

**推送前预检**（不消耗配额，全部本地/只读）：
1. `diagnoseWeChat()` —— 复用现有三态检查，IP 白名单不过直接短路。
2. `assertPushableLayout()` —— §7.5 的第 9 道对账（5 项检查）。
3. 凭据存在性（`describeCredentials()`，**永不回显明文**）。
4. 封面图记录存在且字节非空（`cover-missing` 沿用）。
5. 标题/摘要非空、标题 ≤64 字符（对齐 `LaunchBriefSchema.title` 的 ≤64 约束）。

**失败处理**：`WeChatApiError` 已带 `errcode/classification/hint`（`client.ts:19-31`），沿用 `diagnostics.ts` 的分类。追加一条纪律：**失败时绝不写 `status:'pushed'`**（wewrite 已在 `serialize` 内回填，天然满足）。`40164` → 展示出口 IP 与两条出路（加白名单 / 配代理）；token 过期（40001 等）→ 清 `cachedToken` 重取一次再重试**仅一次**。

**审批文案升级**（`composePushAskReason`）：`即将把《标题》推送到微信公众号草稿箱（仅保存草稿，不群发）。` + 门禁结论（沿用 `describeGateVerdict`） + 新增：稳定版 SHA 前 8 位、第 9 道对账结论摘要、外链图数量、是否 `draft/update` 覆盖式重推。**重推的审批文案必须显式写「将覆盖后台草稿 mediaId 尾 4 位」**。

### 7.8 与「不自动发布」硬规则的关系

pipeline 的硬规则是「未经明确确认不建草稿不调发布接口」。本插件**不放宽**它，而是把它升级为更细的三级确认（`publishTarget` 仍是 `z.literal('draft')`，freepublish 类型层不可达）：

| 级别 | 触发 | 确认方式 |
|---|---|---|
| 自动草稿 | 设置页显式开启 `autoDraft` 且 layout 全绿 | 仍走 `tools/pre-execute` 审批；用户可在审批面板选「本篇记住」 |
| 手动推送 | 工具 `wechat_push_draft` / UI 按钮 | 每次审批 |
| 群发 | —— | **不可达**（`publishTarget` 无 freepublish 取值） |

### 14.3 改名操作要点（下次同类改名直接照抄）

本轮踩到的四个坑，都已固化：

1. **驼峰标识符不能用连字符替换**。`wewriteDeliverablesDefinition` 若按「独立词」规则换成 `wechat-articleDeliverablesDefinition` 会**直接破坏语法**（`tsc` 报一堆 `TS1005`）。必须区分：`wewrite(?=[A-Za-z])` → `wechatArticleXxx`（驼峰），`wewrite` 独立词 → `wechat-article`。
2. **大小写变体比想象的多**。本轮实际出现 **四种**：`dsh-wewrite` / `dsh_wewrite` / `Wewrite`（**216 处，最容易漏**）/ `wewrite`，外加 `WeWrite`。只按两三种写规则必然漏。**改名前先跑 `grep -rhoE '[Ww][Ee][Ww][Rr][Ii][Tt][Ee]' | sort | uniq -c` 做全变体普查。**
3. **要改文件名，不只改内容**。`wewrite-button.tsx` / `commandview-wewrite.tsx` / `wewrite-command.test.ts` 三个文件只改内容会导致 import 解析失败（`TS2307`）。用 `git mv` 保留历史。
4. **目录跳过规则别用裸目录名**。脚本里 `SKIP_DIRS` 含 `'lib'` 会**连 `src/client/lib/` 一起跳过**（`os.walk` 按目录名匹配），导致 7 个源码文件漏改。应只跳根级 `lib/`。

### 15.2 cordis 4.0.4：inject 是硬依赖，**没有「可选服务」语法**

前文 §9.1 写「client 侧 inject 绝不用 `?` 后缀」，现在有源码级定论，且**规则没变**：

- `registry.ts:19` `export type Inject<M = Dict> = (keyof M)[] | { [K in keyof M]?: M[K] }` —— 对象形式的 `?` 修饰的是 **intercept 配置值**（缺省即 `null`），**不是服务名**。
- `registry.ts:71` `Inject.resolve()`：数组形式与对象形式产出**同一个「服务名 → null」映射**，语义完全等价。
- `fiber.ts:238-244`：构造时 `if (isNullable(config)) continue; this.ctx[Context.intercept][name] = config` —— `isNullable`（来自 `@deepseek-ai/cosmokit`，`value === null || value === void 0`）只表示「该服务不设 intercept 配置」。
- `fiber.ts:610-635` `_checkImpl` / `_refresh`：`for (const name of Object.keys(this.inject)) { const impl = this._store[name]; if (!impl) { epoch = INACTIVE; break } }` —— **inject 数组里每个 key 都是硬依赖，缺任何一个 → fiber 永不激活**。写 `conversationEvents?` 这种带 `?` 的名字，会被当成一个字面量服务名，**永久等待**。
- 报错原文：`reflect.ts:144` `cannot get property "${prop}" without inject`；未就绪时 `reflect.ts:159` 改写为 `cannot get required service "${prop}" in inactive context`；`reflect.ts:162` 逐级向父 fiber 上溯并拦跨隔离域读取。
- 绕过 inject 的读法是 `ctx.get(prop, false)`（`reflect.ts:10` 注释「Read a service from the store without the inject requirement」）。
- **官方唯一推荐的可选依赖路径**是 `ctx.inject(deps, callback)`（`registry.ts:176`，语义「the callback is unloaded and re-run whenever a required service changes」）—— 即 wewrite 现有的动态子 fiber 做法，**保留**。
- 插件配置面：`Plugin.Base<T> = { name?; Config?: StandardSchemaV1<any, T>; inject?: Inject; provide?: string|string[]; intercept?: Dict<boolean> }`。配置走 standard-schema 校验，**但「能不能被宿主投影成设置 schema」是另一回事**（见 B1）。

> 修订：§9.1 表格下方那句「rc.7 cordis 不解析」改为「**cordis 4.0.4 同样不解析，且源码级确认**」。

### 15.3 工具层重写规范（替代 §8.1 的宿主约束清单）

**定义面**（`dsh-tools/lib/types/index.d.ts:106-205`）：

```ts
interface ToolOutputDefinition {
  readonly schema: JsonSchemaNode;                                  // 必填
  render(args: unknown, value: JsonValue): ContentBlock[];
  presentationMeta?(args: unknown, value: JsonValue): JsonValue;
}
interface ToolDefinition extends ToolSchema {                      // { deferLoading?: true; name; description; parameters }
  readonly output: ToolOutputDefinition;
  execute(args: unknown, exec: ToolRunContext): Promise<unknown>;
  projectContent?(exec, result): ContentBlock[] | undefined;
  finalizeContent?(exec, result): ContentBlock[] | undefined;      // 必须全函数、不得抛
  timeoutMs?: number;
  isConcurrencySafe?(args): boolean;
  presentCall?(args): ToolCallView | undefined;
  presentResult?(args, result): ToolResultView | undefined;
}
```

`defineTool<const S extends ParameterSchemaSpec, const O extends ValueSchemaSpec>(...)` 给出 `InferArgs<S>` / `InferValue<O>`（推断上限 16 层容器，之后加宽为 `JsonValue`；`const` 类型参数用于让 `required` / `const` / `enum` 保留字面量推断）。

**DSL 规则（逐条来自 `schema.d.ts` + `schema.js` 运行时）**：
- `ParameterSchemaSpec` 是**隐式开放对象根** —— 顶层直接写 `{ article_id: { type: 'string', required: true } }`，**不用**手写 `{type:'object', properties, additionalProperties}`。
- **嵌套 object 的 `additionalProperties` 是必填的**，写错抛 `JsonSchemaError`：`${path}.additionalProperties must be explicitly true or false`。
- 其它编译期错误原文：`${path} cannot declare both type and oneOf` / `${path}.required must be true when present` / `${path}.<key> is not supported by the value schema DSL` / `${path} is circular`。
- **零强制转换**：`type:'integer'` 是独立节点，校验 `isJsonNumber(value) && Number.isInteger(value)`，诊断 `"<path>" must be an integer`。前文的 `coerceInteger` helper **删掉**。
- `default` 只是注解，**永不注入**。
- `JsonSchemaNode` 支持 `type / oneOf / properties / required / additionalProperties / items / enum / const / description / title / default / examples`，**不支持 `$ref` / `pattern` / `min` / `max` / `format` / `anyOf`**；不支持的关键词是**报错**不是忽略。

**执行与错误**：
- `defineTool` 包装器：`const violations = validate(args); if (violations.length > 0) throw new ToolArgsError(violations)` —— **在校验失败时抛异常，不调 `execute`**，由注册表归一化成 `isError` 结果。**前文「校验失败返回值不抛」这条反了：不要试图从 `execute` 里返回错误对象来表达参数非法，因为根本进不到函数体。**
- 每个结局（成功与失败 alike）的 canonical `value` 都要过 `output.schema`，违反则抛 `ToolOutputError(toolName, violations)`。**必须声明判别式 output DTO**（如 `{status:'ok'|'error', ...}`）并保证每个返回都合法。
- `presentCall` / `presentResult` / `isConcurrencySafe` 包装器跑**同一份**校验，但违反时返回 `undefined` / `false`（注释原文：presentation「may run on REPLAY of arbitrary logged args (possibly from an older schema), so it must never throw」）。
- `timeoutMs` **仅声明，注册表绝不强制执行截止时间**；`schemas()` 只白名单 name/description/parameters，**`timeoutMs` 对模型不可见**。要真超时得包 `@deepseek-ai/dsh-tool-call-timeout-policy`（独立包，本规划未解包）或在 `execute` 里自己看 `exec.signal` + `setTimeout`。
- 错误码常量：`TOOL_ABORTED = "ABORTED"` / `TOOL_ABORTED_BEFORE_DISPATCH = "ABORTED_BEFORE_DISPATCH"`（另 `TOOL_TIMEOUT` / `UNKNOWN_TOOL` 来自 dsh-tools 之外）。`ToolErrorInfo = {name, code, reason?}`，`reason` **只作持久化，不进模型可见内容**。
- `ToolExecutionResult` 判别：`{isError:false, value, content, meta?, additionalContexts?, concludesTurn?}` | `{isError:true, error: ToolFailure, content, meta?, additionalContexts?}`。`value` 是执行局部量，**故意不进持久事件**；`meta` 会持久化在 `tool/result`。
- 固定流水线：`tools/pre-execute`（可扩展 allow/deny/ask）→ `ctx.tools.guard()`（单调，只拒不允）→ `tools/execute`（**只允许替换 `signal`**）→ `tools/post-execute` → `projectContent`（在 post 之前安装 content）→ `finalizeContent`（结局物化前最后一次变换，须全函数）→ 只观测的 `tools/result`。
- `ToolRunContext extends ToolExecution` 新增 `deferContext(context: UserMessage): void` 与 `concludeTurn(): void` —— **推送审批与配图这类「要用户拍板但不结束轮次」的步骤可以直接用它们，省掉第二次 LLM 往返**。
- 呈现视图收窄为 `GenericCallView | TerminalCallView | DiffCallView`（search/read/web 只能是**结果**视图），所以旧 `presentCall` 里用 search/read 卡片的写法要折成 `GenericCallView`。

**§8.1 工具表修订**：`timeout` 列含义改为「自实现截止（`execute` 内自建定时器 + `exec.signal`）」，并在 **M0 闸门 4**（工具迁移）落一个共享的 `withToolDeadline(exec, ms, fn)` 工具函数；每个工具的 `output.schema` 统一判别式；`presentationMeta` 仍要求 strict JSON 且 `JSON.stringify→parse` 无损（这一条**保留**，只是入口从 `ToolDefinition.meta` 变成 `output.presentationMeta`）。

### 15.5 调度：宿主 `schedule` 是一等公民，取代 wewrite 的自建 tick

rc.2 提供了**真正的持久化调度器**（`schedule` 服务 + `schedule/changed` 事件），而 wewrite 是手搓的（`dsh-wewrite/src/host/scheduler/service.ts:1-151`：`createOccurrenceClaimer` / `scanOccurrences` / `setInterval` 泵，`DEFAULT_MISFIRE_GRACE_MS = 10*60*1000`、`DEFAULT_TICK_MS = 30*1000`、occurrence key `${schedule.id}:${next}`；接线在 `service.ts:103`、启动 `:393`、停止 `:404`）。

`schedule` 契约：
- `create(sessionId, ScheduleCreateRequest, signal?)` / `list` / `catalog` / `history` / `delete` / `update`（后者乐观锁，`request.expected` 传完整观测记录，失配码 `schedule_not_found | schedule_ended | schedule_conflict`）。
- `ScheduleCreateRequest = { prompt; title（必填，缺失/空白/过长 → `invalid_prompt`，**不从 prompt 推导**）; after_seconds?; at?: AtInput; every_seconds?; daily?: DailyInput; weekly?: WeeklyInput; cron?: CronInput }`。记录形态：`after` / `at` / `every` / `daily`（`time`+`timeZone`）/ `weekly`（`time`+`timeZone`+`weekdays:number[]`）/ `cron`（`expression`+`timeZone`）。**入参 snake_case、记录 camelCase**（和 wewrite 自己的 RPC 边界同一个不对称）。
- 错误码：`invalid_prompt | invalid_selector | invalid_rule | invalid_time_zone | not_future | time_out_of_range | frequency_too_high | internal_error`。`history` 的 `limit` 必须是 1..100 的安全整数。
- **投递前提**：「`sessionPersistence` is a load-order requirement rather than a directly called service: a delivery commits only when `ctx.sessions.flush()` reports that a `session/flush` listener participated.」→ 定时任务必须在**装了 `session-persistence-jsonl` 的会话**里才有意义。
- **没有 misfire grace / occurrence claim 语义** → §4.x 里「同一篇文章同一时刻只推一次」的幂等键仍要留在自己的 domain 表里。

⚠️ 但**随发行版的 web 组合不含 `schedule` 行**：服务在（实测存在），行不在。要用必须在插件管理页装 `@deepseek-ai/dsh-experimental-schedule-bundle` 0.2.0-rc.2（`time-context` + `schedule` + `ui-schedule`，当前 `enabled: false`）并在自己的 patch 里插行。**建议：定时发布做成「检测到 `ctx.get('schedule')` 可用就走宿主、否则回落到自建 tick」的双实现**，并在设置页说明差异。

`timer` 服务（rc.2 新增）取代裸 `setInterval`：`timeout(cb,delay):()=>void` / `timeout(delay):Promise<void>` / `interval(cb,delay):()=>void` / `interval<R>(delay): AsyncIterableIterator<void,R,void>` / `throttle(cb,delay,noTrailing?)` / `debounce(cb,delay)`，全部返回 fiber 拥有的 disposer。

`jobs` 服务（抽象，适合跑长管线）：`start(spec): JobId`（**同步返回**）/ `kill(id, caller?, reason?)`（返回 `'requested'|'already-finished'`）/ `wait(id, timeoutMs, caller?, signal?)` / `list` / `get` / `read` / `readAt` / `remove` / `attachController` / `events`。

### 15.6 agent 生命周期：用 `setup` 取代全局 `agent/created` 监听

rc.2 的正解是 `CreateAgentOptions.setup`：


**两条新约束（会改变前文 §9 的设计）**：

1. **单 View 会让 tab 栏消失。** `conversation.view` 的选择规则是「有效且已注册的持久化偏好优先 → 已注册的 `chat` → 否则不渲染 View；**绝不选第一个已注册 View**」，且**可用 View 少于两个时隐藏 View 标签栏**。前文 §9.1 只注册自己的一个 view（`id: 'wechat-article'`），宿主自带 `chat` —— 刚好两个，tab 栏不会出现；但**如果哪天 `chat` 未注册，就只剩一个 View 且 tab 栏直接消失，插件面板进不去**。→ 记一条自检：`conversation.view` 注册后断言 `chat` view 在位。
2. **`conversation.composer` 在 0.2.0-rc.2 是 chain（`select` 选择器），不是普通 list**，且「业务包仅可在一个 Remote waterfall request pending 期间安装 entry」，安装必须 try/finally dispose。前文若打算改写 composer（插入排版按钮）应改走 `conversation.input.right`（普通 list，无此限制）；只有真的要**接管** composer 才用 chain，且「takeover 下 shell 保持默认 composer 挂载」。

另外几处与前文预期不同的 rc.2 事实：
- `main` 是 keyed（`open: any string the owner dispatches`，已占 `conversation`），`main.conversation` 由宿主 ui-conversation 插件占据；`conversation.header`（含 `leading` / `session.header.{actions,corner,utilities,lineage}`）是 rc.2 新增的**常驻**会话头，排在 `conversation.content` 之外。
- **右栏族是全新的**：`rightbar` 下 `sidebar.right.pane.tab`（每会话一个停靠面）+ `sidebar.right.tab.document.*`（文档预览/office.pdf/act回答）。wewrite 时代完全没有这一族。若希望「编辑页」以宿主右栏停靠而非自绘，优先用 `sidebar.right.pane.tab` 而不是自建 overlay。
- `conversation.composer.bar` 的 registration 是空（`single`），`conversation.input.activity` 是 `single` 且 `replaceRisk: shadows-shipped-ui`（**不要占**，它被模型选择器与发送按钮之间的紧凑动作独占）。
- `conversation.chat.node` 当前已贡献 19 个 kind（`assistant-step` / `command` / `command-input` / `compaction` / `context` / `manual-compaction` / `model-retry` / `question-reply` / `steering` / `system-prompt` / `tool-call` / `turn-error` / `turn-max-tokens` / `turn-process` / `turn-tail` / `turn-trigger` / `unknown` / `user` / `workflow-run`）。⚠️ **本条已修正前稿**：keyDomain **不是封闭集**，`ChatNodeDataMap` 是**声明合并开放接口**，`ChatNodeKind = Extract<keyof ChatNodeDataMap, string>` 随之开放 —— 逐字注释「Merge-extensible payload registry keyed by final Chat renderer kind」。所以**可以自造 kind**（`declare module` 扩 `ChatNodeDataMap` 再用同 key 注册渲染器）。前文 §9.3「deliverables 走官方 ui-deliverables 模式」仍然更省事，但不再是硬约束。

### 15.14 `connection.rpc` 契约定案（`HostConnectionRpc` / `ClientConnectionRpc` 逐字读出）

这是 §15.10 长期开放的那一项 —— **`HostConnectionRpc` 本体已读到**（`@deepseek-ai/dsh-client-connection@0.2.0-rc.2` `package/lib/types/rpc.d.ts`），同时**推翻了前文继承自 rc.7 的一条架构约束**。

**① `handle` 的第三个参数 `{authority:'loopback'}` 在 rc.2 不存在。** 逐字签名只有两个参数：

```ts
/** Host registry for logical RPC channels carried by the current transport. */
export interface HostConnectionRpc {
    handle(channel: string, handler: ConnectionRpcHandler): () => Promise<void>;
    intercept(channel: '/api', matches: ConnectionRpcEndpointMatcher, handler: ConnectionRpcHandler): () => Promise<void>;
}
```

全包 grep `authority|loopback` 只命中一条与权限无关的注释（`:185` 谈 baseUrl 的 authority 段），**`.d.ts` 与 bundle 里都不存在第三个 options 参数**。→ 前文 §9.4 与 wewrite `docs/tech-architecture.md:54`（F13）继承的「通道 authority=loopback」这条契约**在 rc.2 已作废**。wewrite `src/host/rpc.ts:180` 的 `rpc.handle(RPC_CHANNEL, handler)` 恰好是两参（无类型错误），但**运行期必然抛 `webServer` 错** —— 见 §15.14b(2)①。`{ authority: RPC_AUTHORITY }` 属旧 host 适配层，新插件不要继承。**若仍需限制调用来源**，rc.2 的手段是走 `connection.fetch` 的 `/api` 围栏（宿主的 `admit(request)` / `authorizeIndex(request, response)` 对每条 `/api` 请求统一施加）或自写归属判定 —— **不是 authority 字段**，也**不是** `intercept`（`/api` 独占，已被 `dsh-api-gateway` 占用）。

**② handler 的返回值形状没变，但失败体的 `details` 是必填。**

```ts
export type ConnectionRpcHandler = (endpoint: string, payload: unknown, signal: AbortSignal, peer: PeerScope) => Promise<ConnectionRpcHandlerResult>;
export type ConnectionRpcHandlerResult =
  | { readonly ok: true; readonly value: unknown; readonly attachments?: readonly ConnectionRpcAttachment[] }
  | { readonly ok: false; readonly error: ConnectionRpcFailure };
export interface ConnectionRpcFailure { readonly code: string; readonly message: string; readonly details: object; }
```

⚠️ 这让 wewrite 记忆坑 `dsh-host-rpc-error-code-must-be-in-host-enum` **依然成立且更硬**：插件自有码（`PI_AI_ERROR` / `digest-timeout` / `llm-not-configured`）不能直接放进 `code`。但 rc.2 的 carrier 约束已从「宿主 39 个枚举码」收窄为 **`@deepseek-ai/dsh-typert-protocol` 的 `RemoteErrorDetailsMap` 三个 carrier code**（`gateway/bad-request` 带 `issues`、`gateway/cancelled`、`gateway/internal`，map 是 merge-extensible）。**修法不变**：信封 `code` 统一用 `internal`，真实码以 `[code] ` 前缀留在 `message`，并补 `details: {}`。

**③ `call` 直接返回判别联合，且新增 `open` 流式方法。**

```ts
export interface ClientConnectionRpc {
    call(channel: string, endpoint: string, payload: unknown, signal?: AbortSignal): Promise<ConnectionRpcResult<unknown>>;
    readonly open?: (channel: string, endpoint: string, payload: unknown, signal: AbortSignal, uplink?: AsyncIterable<unknown>) => AsyncIterable<unknown>;
}
export type ConnectionRpcResult<T> = { readonly ok: true; readonly value: T } | { readonly ok: false; readonly error: ConnectionRpcFailure };
```

`call` 的逐字注释确认「correlation stays inside Connection」——**`rpcId` 由传输层内部管，插件不需要也不能自带 correlation id**。wewrite `src/client/lib/rpc.ts:81` 的 `raw.result ?? raw` 双形态兜底**恒定走 `raw` 分支**，是死代码（冗余非阻塞，可清理）。`open` 是**可选方法**且「Browser transports omit this method」→ **客户端代码不能假设它存在**，需要流的端点（如 run 进度推送）必须先探测 `typeof rpc.open === 'function'`。二进制附件走 `ConnectionRpcAttachment{path, bytes}`（`path` 是「结果中的 null 占位路径」，`bytes` 走传输层分离）→ **排版产物里的图片不要 base64 塞进 RPC result**，这是宿主给的正道。

### 15.14b ★★ 端点注册面定案：`rpc.handle` 已死，改走 `connection.fetch` 精确路由（2026-10-07 实测结案）

§15.14 读的是 `.d.ts` **契约**；本节记的是**运行时真相**，两者结论不同。契约说 `handle(channel, handler)` 存在，实测它**必然抛错**。

#### (1) 断点定位：不是 rc.2 的变化，是 0.1.5-rc.1（2026-09-10）

用 `npm pack` 取六个历史版本逐行对照 `dsh-client-connection` 的 `inject` 声明：

| 版本 | `inject` | 发布日 | 面板 |
|---|---|---|---|
| 0.1.2-rc.1 | `['webServer','credentials']` | 2026-09-03 | **可通** |
| 0.1.5-rc.1 | `['credentials']` | **2026-09-10** | **webServer 被移除 → 失效** |
| 0.1.5-rc.3 / 0.1.7-rc.1 / 0.2.0-rc.1 / 0.2.0-rc.2 | `['credentials']` | — | 同上 |

wewrite 的面板真实截图提交在 **2026-08-19**（`re-shoot all 6 UI screenshots from v0.1.4`），v0.5 的 `live H06 全合同真跑` 在 **08-24** —— 都在断点之前。**所以这是 DSH 的一次静默破坏性变更：插件代码一行没改，面板就哑了。**

⚠️ 对照方法论：只比 rc.7 与 rc.2 会得出「两版一致、不是新变化」的**错误结论**（rc.7 已在断点之后）。**追溯必须回到断点之前的版本。**

#### (2) 三条注册路径逐一封死（均为实测）

**① `rpc.handle(channel, handler)` —— 必然抛错。**
宿主实现（`lib/index.js` 的 `register`）内部执行 `owner.webServer.register(route)`，而 `owner` 来自 `get rpc() { const owner = this.ctx }` —— 那是 **connection 服务自己 fiber 的 ctx**，它没有 webServer 依赖：

```
CATCH cannot get property "webServer" without inject
```

⚠️ 在插件自己的 `inject` 里补 `webServer` **无效**（实测：补了仍报同一错，因为缺依赖的是 connection 的 fiber，不是我们的）。该异常发生在 `registerAgentTools` / `registerWeChatArticleCommand` / `startScheduler` **之前**，被 `apply()` 的外层 catch 吞掉 → **工具、命令、调度器整块不注册**。这才是「Agent 调不到 `wechat_*` 工具」的真根因（**不是**闸门 `agentToolsEnabled` 默认 false —— 探针实测 `gate=true configDefault=true`）。

**② `rpc.intercept('/api', …)` —— 独占槽已被占。**

```
CATCH connection: shared RPC channel "/api" already has an interceptor
```

`/api` 是保留通道（`assertChannel` 里 `channel === "/api"` 直接抛），且 `registerInterceptor` 独占（`if (this.interceptors.has(channel)) throw`）。占用者是宿主 `dsh-api-gateway`（`dsh-api-gateway/lib/index.js:624`），无插件级 API 往它的 dispatcher 追加端点。

**③ Typert registry —— 普通插件拿不到。**
`TypertLocalRegistry` 只有 `get` / `hasSeen` / `list` / `subscribe`，**没有 `register`**；本地端点仅能由**代码生成的 Typert 包**贡献（需 `model` + `TypertCodec` + 真 cordis Service 提供 `service` 键）。四个 registry 里只有 `TypertRemoteRegistry.register`，那是注册 **Remote 贡献**，不是本地端点。

#### (3) 采用：`connection.fetch` 精确路由（官方公开面，四个官方插件在用）

```ts
connection.fetch.register({ path, methods, requestBody: 'buffered' | 'streaming', fetch })
```

约束只有三条（`assertFetchRoute`）：path 落在 `/api` 之下、每段匹配 `/^[A-Za-z0-9_$.-]+$/`（`endpointFromPath`）、methods 非空不重复。**无独占限制、不依赖 webServer**，且匹配**优先于** `/api` 的 RPC interceptor（`createSharedFetchHandler` 先查 `fetchRoutes` 再查 `interceptors`）。

在用的官方插件：`dsh-api-session-controller`（`/api/file`）、`dsh-session-log-export`、`dsh-client-ui-deliverables`、`dsh-client-file-upload`（POST + streaming）。

**代价**：fetch 面是**精确**路由（`fetchRoutes.get(pathname)` 查表，无前缀匹配），故 23 个端点各注册一条，而非一条前缀路由。

**红利：契约零改动。** 官方 fetch 路由的响应信封与我们既有的完全一致：

```ts
// dsh-client-file-upload 的 handleFileUploadHttp
result = { ok: true, value: await service.uploadStream({...}) };
// 失败：{ ok: false, error: { code, message, details } }
```

故 `dispatch`、双端 zod 校验、微信 errcode 分类（40164 / AUTH / TIMEOUT / RATE_LIMIT）、错误截断**全部原样保留**，23 个端点名也不必改（22 个已是 `service/method` 两段式，天然贴合；只有 `snapshot` 是单段但作为精确路径无妨）。

客户端对应改为裸 `fetch('/api/dsh-wechat-article/<endpoint>', {method:'POST'})`，鉴权靠同源 cookie（宿主 `/api` 围栏对每条请求生效，官方 fetch 路由客户端同样用裸 fetch）。

#### (4) 实测验收：23/23 端点 HTTP 200 信封

对活着的 rc.2 web 宿主逐个 curl（`/tmp/verify-final.py`）：**23 个端点全部返回 HTTP 200 + 合法信封**。其中错误路径也通（`article/rewrite` → `[llm-not-configured] 尚未配置默认模型…`，`run/detail` 查不到 run → `ok:false`）。

### 16.2 采集架构：镜像 wewrite 的三层模式

wewrite 的素材获取架构（`src/host/pipeline/steps/topic.ts`，126 行）是三层，**逐层照搬**：

```ts
// 单源失败永不抛出、永不清空其他源；失败以 {sourceId, message} 收集
```

### 16.3 源健康探针（把已发生的事故固化成机制）

那份采集 prompt 里最重的一段是 2026-09-12 的源健康纪律，它记录了**三类真实误判**：

- **照抄历史失效清单而不真探测** → 12 条申报里 8 条实测正常
- **只量字节数没看状态码** → Databricks 旧地址 404，但 404 页面本身 671KB HTML，被误判为「在线可用（671KB）」
- **把探测失败当成源失效** → HTTP 000 / 超时被写进「真失效源清单」（2026-09-17 事故后新增禁令）

故本插件的探针把判定**收敛为四态**，并把"必须附证据"做成代码约束：

```ts
export type ProbeVerdict = 'ok' | 'dead' | 'low-frequency' | 'unprobed';

export interface SourceProbe {
  readonly sourceId: string;
  readonly verdict: ProbeVerdict;
  readonly http?: number;            // 000/超时 = 探测通道失败
  readonly contentType?: string;     // rss | atom | xml | html | json
  readonly itemCount?: number;
  readonly latestAt?: string;
  readonly evidence: string;         // ★ 必填：状态码 + 内容类型 + 条目数；缺证据不得判 'dead'
}
```

**判据（写成代码，不写成 prompt 里的自然语言）**：

| 条件 | verdict | 禁令 |
|---|---|---|
| HTTP 200 且 contentType 是 feed/json | `ok` | — |
| HTTP 非 200 / 200 但返回 HTML/SPA | `dead` | **必须附 `http` + `contentType` + `itemCount`** |
| HTTP 200、feed 正常但窗口内无新条目 | `low-frequency` | **不得写成「RSS 失效」**——低频是正常现象 |
| HTTP 000 / 连接超时 / 空响应 | `unprobed` | **严禁并入 `dead` 清单** |

另外：**`dead` 清单是白名单制**（源采 prompt 明写「本条④是真失效源的白名单，禁止自行增删」），新增一条 `dead` 必须过证据校验；这正好落在 §15.7 的 `ctx.invariants.register()` 上——把「证据缺失的 dead 判定」做成**受管的不变量违规**，而不是一行被吞的 warn。

### 16.5 预算与停手：把「run 报成功但没落盘」堵死

那份 prompt 记录的 2026-09-20 事故值得原文引用，因为它定义了一类**整个插件都必须防的失败模式**：

> 定时 run 因 SearXNG 降级，agent 反复换策略重试搜索，耗尽轮次/上下文预算，在「即将写文件」一步被截断，**run 却被框架记为 success=true、未落盘、全链路无告警**。根因：①成功判据只看 run 是否无异常退出，不校验产出物；②prompt 缺搜索预算上限与「达标即停手落盘」约束。

三个机制（全部写进代码，不靠 prompt 自律）：

1. **预算计数器**：`ResearchContext.budget = { limit, used, retriesBySource: Map<string, number> }`，每次 `ctx.web.search/fetch` 前递增；达上限立即停止采集、用已有候选落盘。
2. **达标即停手 + 增量落盘**：收集到 ≥ `minItems`（默认 10）立刻停；**先写草稿再补**——即使只有 5 条也先落盘，再在草稿上追加。`ctx.fs.writeText` 的原子写 + `expected: 'replaceIfVersion'` 正好支撑增量追加。
3. **落盘后断言（成功判据改成校验产物）**：文件存在 ∧ `count(条目头) ≥ floor`，否则 research 步 **failed**，并在 run 记录里写明「产出校验未通过」。**这是对上游「成功判据只看进程退出码」的直接修正。**

### 16.6 跨轮去重与编号

**指纹**：`MaterialItem.id = sha256(normalize(url)).slice(0,16)`，`normalize` 做去尾斜杠、剥 `utm_*`/`ref`/`source` 查询参数、统一小写 host。写入前用指纹查 domain `materials` 表（§16.7）——**不靠 grep 文本文件**（上游用 grep，是因为它没有索引；我们有 storage domain，用索引更快更准）。

**编号**：上游那条命令值得引以为戒——

```bash
NEXT=$({ grep -oE '^\| *[0-9]+ *\|' 金融AI应用发展/素材库/专题总表.md; grep -rhoE '^### #?[0-9]+' 金融AI应用发展/素材库/2026-*.md; } | grep -oE '[0-9]+' | sort -n | tail -1); echo $(( ${NEXT:-0} + 1 ))
```

它严格限定只认两种权威信号（总表行首序号列、素材条目标题行），因为**旧写法「全文件 grep `#数字` 取最大值」把 MCP 的 GitHub issue `#1933` 当成了素材号**，导致从 `#1934` 起跳、与真实序号脱节。

→ 插件侧**不引入这种文本编号**：`materials` 表用自增序号字段或 ULID，总表/素材文件里的序号由**渲染时**从索引生成，从根上消除「文内 `#数字` 污染编号」这一整类事故。若必须保持与既有素材文件的编号连续（迁移场景），则实现一个**只认条目头**的解析器，并在测试里钉死「文内 issue 号不得影响编号」。

### 16.7 数据模型（新增两张表）

```ts
// 存储单元仍是 dsh_wechat_article（下划线，§6.1）；version 递增到 2
materials: { valueSchema: MaterialRecordSchema },
exemplars: { valueSchema: ExemplarRecordSchema },
```

**`MaterialRecordSchema`**（指纹索引 + 状态流转；**不含正文**，正文在工作区文件里）：

| 字段 | 说明 |
|---|---|
| `v` / `id` | `id` = URL 指纹（跨轮去重键） |
| `title` / `url` / `sourceId` | 来源 |
| `publishedAt?` | ISO；缺失时存 `null` 且另记 `dateUnverified: true` |
| `topic` / `style` | **`z.string()`，不是 `z.enum`** —— 白名单由 `research.topics/styles` 配置提供，**运行期**用研究门禁 `taxonomy-whitelist` 校验。⚠️ 这里若写成 `z.enum([...])` 就把某个项目的主题名烧进了 domain schema，属 §2.3 禁止清单 |
| `keyPoints` | **`z.record(z.string(), z.string())`，不是固定四字段** —— 段数与标签由 `research.keyPointFields: {key,label,required}[]` 配置决定，schema 只保证「键是字符串、值是字符串」。同理，写成 `{problem, method, experiment, relevance}` 就是把某个项目的要点结构烧进了 schema |
| `status` | `'collected' \| 'selected' \| 'written' \| 'published' \| 'discarded'` —— 对应上游专题总表的五态流转（待选/选中待完成/已完成/完成待发布/已发表 + 舍去） |
| `collectedFromRunId` | 哪次 run 收的（溯源） |
| `contentPath` | 素材文件相对路径（内容真相源的位置） |
| `dupOf?` | 去重命中时指向已收录条目 |
| `collectedAt` / `updatedAt` | |

**`ExemplarRecordSchema`**（风格学习，§16.9）：`v` / `id` / `title` / `sourceUrl` / `rawPath`（范文原文）/ `profile`（风格画像，`strictObject`）/ `learnedFrom: 'import' | 'edits'` / `createdAt`。

**文件 vs domain 的张力（要显式裁决）**：§0 的决策是「工作区文件为准，domain 只存索引」。素材这里**两者都要**，但职责必须分清：

- **素材文件 `素材库/YYYY-MM-DD.md` 是内容真相源**（人可读、可 git、可人工改）
- **domain `materials` 表是指纹与状态索引**（跨轮去重、状态流转、UI 列表、run 溯源）

这与 §0 不矛盾：索引不是第二份真相，它只存**可以从文件重算的东西 + 文件里没有的状态位**。冲突时的仲裁规则：**正文以文件为准；状态以 domain 为准**（因为状态是人工点选产生的，文件里没有）。

⚠️ 上游有一条反直觉纪律必须继承：**「专题总表只记录用户选中的素材，未选中的不进总表」**，且该采集任务**一律不写总表**。→ 插件里对应：`status='collected'` 只在 domain 表里，**渲染总表时只输出 `status ∈ {selected, written, published}` 的行**。把这条做成渲染器的默认过滤，而不是让人记得。

### 16.8 产出契约与**领域配置外置**（本章最重要的设计决定）

上游素材文件的结构（**实测 `素材库/2026-10-06.md`，341 行、19 条、序号 #517–#535；以下全部只作证据引用，其主题名、风格名、字段标签、路径均是那个项目的私有约定，绝不进入本插件的代码或默认值**）：

```
# 素材库 YYYY-MM-DD
> 采集日期 / 时效窗口 / 检索通道 / 执行模型
## 源健康探针结论（本次运行前实测）      ← 表格：源 | HTTP | 类型 | 判定
### 真失效源（本次新增证据）
### 低频无更新（窗口内无有效素材）
### 本次未探
---
## AI研发流程          ← 五主题分节
### #517 arXiv 2026-10-05：<标题>
**来源**: <url>（分类，日期）
**核心要点**:
- **研究问题**：…
- **核心方法**：…
- **实验**：…（须含可量化指标）
- **对金融场景的参照**：…        ← 核心价值，禁止删除
**主题 + 推荐风格**: #AI研发流程 #风格:技术讲解类
## Agent技术 / ## 金融AI工程实践 / ## 模型与能力 / ## Github热门项目
## 供用户挑选的建议选题（3-5 条）
## 跨轮去重说明
## 公众号补充源说明
```

**但这份规格里有大量领域特定的东西，绝不能硬编码进插件**：

| 上游写死在 prompt 里 | 插件里应该是什么 |
|---|---|
| 五主题（AI研发流程/Agent技术/金融AI工程实践/模型与能力/Github热门项目） | `research.topics: string[]` 配置；**运行期**用门禁 `taxonomy-whitelist` 校验，**不得写成 `z.enum`**（那会把某个项目的主题名烧进 schema，§16.7） |
| 四风格（技术讲解类/案例分享类/新闻分享类/观点洞见类） | `research.styles: string[]` 配置；默认值**留空数组**，不预置任何一个项目的风格名 |
| 20+ 具体源（arXiv 四类 RSS、OpenAI/DeepMind/…、Stripe/Netflix/… 13 个国内源） | **声明式源注册表配置**（YAML/JSON），不再写进代码 |
| 「金融场景的参照」这第四段 | `research.keyPointFields: [{key,label,required}][]` —— **段数与标签全可配，默认不预置任何字段名**。下表左列的「研究问题/核心方法/实验/对金融场景的参照」只是**上游项目的实例**，不是我们的默认值 |
| 时效窗口「最近 3 日」 | `research.windowDays: number` |
| 「≥10 条停手」「条目下限 5」「预算 40 次」「同源重试 2 次」 | `research.minItems / floor / budget / maxRetriesPerSource` |
| Obsidian 镜像路径、专题总表、git 提交纪律 | **项目侧约定，不进插件**（见下） |

**这条边界是本章的核心判断**：上游把这一切写在一份约 4000 字的 prompt 里，代价是**每次调参都要改 prompt，且纪律靠模型自律**（所以才会有「事故固化说明」一节接一节地往上叠——`2026-08-30`、`09-01`、`09-08`、`09-12`、`09-13`、`09-14`、`09-17`、`09-20`）。插件化时**必须把它拆成「代码里的机制」+「配置里的领域数据」**，否则只是把 prompt 换成另一段更长的 prompt。

**镜像/提交这类项目侧动作不进插件核心**，但可以通过 §8 的工具面暴露为可选动作：`wechat_material_mirror`（走项目自己的固化脚本，插件只负责调用与校验 SHA-256）。理由：上游为此写了 20+ 个一次性脚本（`obsidian_mirror_*.py`），说明这类动作的可变性极高，**属于项目适配层，不属于插件**。

### 16.9 风格学习（F12 三件套）

上游三个资产（`FACTS.md:40`）与映射：

| 上游 | 作用 | 插件实现 |
|---|---|---|
| `fetch_article.mjs` | 范文导入 | `wechat_exemplar_import` 工具：收 URL 或本地 .md → `ctx.web.fetch` 取正文 → 存 `<slug>.md` |
| `extract_exemplar.mjs` | 范文提炼 | 一次 `ctx.llm.stream` 产出结构化的**风格画像**（句式/结构/语气/开篇收尾套路/常用词）→ `<slug>.profile.json` |
| `learn_edits.mjs` | 学用户改稿 | 对比 run 产出的 `draft` 与用户最终保存的 markdown，diff → 提炼偏好规则 |

**破解「重交互」这个砍掉理由**：F12 被判 Won't 的归类是「重交互功能」。但 `learn_edits` 在本插件里可以做到**零交互**——因为

- run 产出的成稿本来就在 domain（`ArticleRecord.markdown` 的历史版本 / `StepRecord.metrics`）
- 用户改稿后的最终 markdown 也在 domain（`article/save` RPC 写入）
- **两者都在手上，diff 是免费的**

所以设计成：每次用户保存文章时，若与最近一次 run 产出的 draft 有差异，就把 `{旧, 新, diff}` 记入 `editSamples`；累积到阈值（如 20 组）后跑一次 LLM 提炼，产出「账号偏好规则」。这样**导入/提炼也不是必答题**——`fetch_article` 与 `extract_exemplar` 是纯加分项，用户可以一辈子不用。

**注入点**：走 §15.7 的 `ctx.systemPrompt`——

- `systemPrompt.section({...})` 注入稳定片段（范文画像摘要、账号偏好规则）
- `systemPrompt.variable(name, provider)` 注入随 run 变化的量（本次选中的范文清单）
- 都是 `() => void` disposer，挂 `ctx.effect`

⚠️ 注意 §15.7 记的 rc.2 事实：系统提示是**一等 session 事件**（`system/message`，`source:{kind:'system-prompt'}`），不是每请求字符串。所以风格片段一改就是一次 system prompt 变更，**会使该会话的 prompt cache 失效**——提炼频率要低（阈值触发，不是每篇都提炼），否则 KV cache 成本会很明显。

### 16.10 与 DSH 0.2.0-rc.2 的接合点

| 接合点 | 用法 | 依据 |
|---|---|---|
| 采集传输 | `ctx.web.fetch` 拿 RSS/arXiv/GitHub API（直接 HTTP，非搜索）；`ctx.web.search` 做域名兜底 | §16.2 实测签名 |
| 新增 inject | `'web'`、`'schedule'`（定时采集）、`'invariants'`（探针证据校验）、`'systemPrompt'`（风格注入） | §15.15 服务表 |
| 定时采集 | §15.5 的**双实现**：`ctx.get('schedule')` 可用则走宿主（注意随发行 web 组合不含 `schedule` 行，需 `dsh-experimental-schedule-bundle`），否则回落 `timer.interval` 自建 tick | §15.5 |
| 探针不变量 | `ctx.invariants.register('dsh-wechat-article', (ctx, fail) => …)`：证据缺失的 `dead` 判定、`unprobed` 混入 `dead`、越界主题 | §15.7 |
| 素材文件写入 | `ctx.fs.writeText`（原子 + `expected:'replaceIfVersion'` 支撑增量追加）；**不得插 `dsh-fs-local`** | §15.8 |
| 素材图落盘 | `ctx.attachments.saveImage` → `imageHostPath`；domain 只存索引 | §6.1 |

**研究步的 LLM 调用**：筛选判定（四项标准）走 `ctx.llm.stream`，但必须经 `resolveCallConfig` 拿权威配置、不要把 `provider`/`model` 拼在 `execute` 里（§15.3 第 3 条）。

### 16.12 本章新增坑（8 条，机器可读版进 `docs/porting-pitfalls.jsonl`）

| # | id | 症状 | 修法 |
|---|---|---|---|
| 1 | `dsp-collect-success-without-artifact` | **run 报 success 但文件根本没落盘**，全链路无告警 | 成功判据改成校验产物（文件存在 + 条目数下限），不达标即 failed —— 上游 2026-09-20 事故 |
| 2 | `dsp-collect-budget-exhaustion-truncation` | 搜索源降级后反复重试，耗尽轮次预算，在「即将写文件」一步被截断 | 预算计数器 + 同源重试 ≤2 + **达标即停手、先写草稿再补** |
| 3 | `dsp-probe-failure-misjudged-as-dead-source` | HTTP 000/超时被写进「真失效源」清单，导致真实可用源被长期弃用 | 四态判定；`unprobed` 独立成态；`dead` 必须附状态码+内容类型+条目数 |
| 4 | `dsp-copied-stale-failure-list` | 照抄历史失效清单，12 条申报里 8 条实测正常 | **采集前先跑探针，以其输出为准**；禁止引用历史清单 |
| 5 | `dsp-bytes-not-status-code` | 404 页面 671KB HTML 被当成「在线可用（671KB）」 | 判定必须看 HTTP 状态码 + 内容类型，**不得只看字节数** |
| 6 | `dsp-inline-hash-pollutes-numbering` | 文内 GitHub issue `#1933` 被当成素材号，编号从 `#1934` 起跳脱节 | 编号只由索引生成；文本编号解析器只认条目头，测试钉死 |
| 7 | `dsp-cross-round-duplicate-material` | 放宽时效窗口后旧素材重新浮出，被重复收录、重复编号 | 写入前用 URL 指纹查 domain 索引；命中即跳过并记 `dupOf` |
| 8 | `dsp-low-frequency-written-as-dead` | 源「窗口内无新条目」被写成「RSS 失效」 | `low-frequency` 与 `dead` 分列；低频是正常现象 |
